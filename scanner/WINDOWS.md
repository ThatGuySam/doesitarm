# Windows scanning

Windows downloads and local files use the existing Rust `ReadAt` API in the CLI, browser Wasm, and Worker Wasm. The browser shows Windows architecture evidence and, when the product can be matched, a candidate from the Does It ARM Mac catalog. A Windows result describes the submitted artifact.

## What runs on Windows on Arm

| Evidence | What it means |
| --- | --- |
| ARM64 | The binary or declared application package targets the ARM64 Windows ABI. |
| ARM64EC | Code compiled for ARM64EC executes on Arm and interoperates with x64 code in the same process. Any x64 code in that process executes under emulation. |
| ARM64X | The image has both ARM64 and ARM64EC/x64-compatible views. It can be loaded by either ABI on Windows 11 on Arm. |
| x86 or x64 | An ordinary user-mode binary with this architecture requires emulation on Windows on Arm. Windows 11 24H2 and later use Prism. Windows 10 on Arm supports x86 emulation. Drivers need a supported native architecture. |
| .NET AnyCPU | An IL-only PE32/I386 assembly can use the installed runtime's architecture if its dependencies and flags permit it. 32-bit required targets x86. 32-bit preferred records a preference for the 32-bit runtime. |
| Neutral or unknown | A neutral package, setup bootstrapper, incomplete inventory, or an unsupported format leaves app-wide architecture or runtime behavior unresolved. |

These distinctions come from Microsoft's [ARM64EC and final PE identification](https://learn.microsoft.com/en-us/windows/arm/arm64ec), [ARM64X ABI](https://learn.microsoft.com/en-us/windows/arm/arm64x-build), [Prism and emulation](https://learn.microsoft.com/en-us/windows/arm/apps-on-arm-x86-emulation), and [Windows on Arm FAQ](https://learn.microsoft.com/en-us/windows/arm/faq). The [ECMA-335 CLI specification](https://ecma-international.org/publications-and-standards/standards/ecma-335/) and Microsoft's [CorFlags documentation](https://learn.microsoft.com/en-us/dotnet/framework/tools/corflags-exe-corflags-conversion-tool) define the CLR flags.

## Method

- **PE/COFF.** Check DOS magic, `e_lfanew`, the PE signature, COFF Machine, the executable-image flag, and the PE32/PE32+ optional header. Use section raw-data extents to map RVAs. Read only the relevant CLR, Load Configuration, and version-resource entries. Subsystem and original Machine remain available in JSON. Machine values include x86 (`0x014c`), x64 (`0x8664`), and ARM64 (`0xaa64`). Linked ARM64EC images generally retain the x64 machine field. A mapped CHPE metadata pointer and code-map extent distinguish them. An ARM64 image with a bounded type-6 ARM64X dynamic relocation distinguishes the hybrid image. The scanner also recognizes explicit `0xa641` and `0xa64e` identifiers in PE images. [Microsoft PE format](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format) · [VS_VERSIONINFO](https://learn.microsoft.com/en-us/windows/win32/menurc/vs-versioninfo) · [LLVM COFF structures](https://github.com/llvm/llvm-project/blob/main/llvm/include/llvm/Object/COFF.h) · [LLVM dynamic relocation reader](https://github.com/llvm/llvm-project/blob/main/llvm/lib/Object/COFFObjectFile.cpp) · [GNU Binutils PE constants](https://gnu.googlesource.com/binutils-gdb/+/refs/heads/master/include/coff/pe.h)
- **EXE installers.** Detect the Inno offset marker or RCDATA, NSIS firstheader, WiX Burn section, Squirrel setup resource or version markers, and a bounded 7z self-extractor signature. Installer wording in version metadata can identify a generic setup program. Electron-builder's NSIS and Squirrel output uses those respective formats. `bootstrapper_architecture` refers to the setup program. Payload architecture stays unknown for opaque stubs and self-extractors. [Inno Setup loader structures](https://github.com/jrsoftware/issrc/blob/main/Projects/Src/Shared.Struct.pas) · [NSIS firstheader](https://github.com/kichik/nsis/blob/master/Source/exehead/fileform.h) · [WiX Burn section](https://github.com/wixtoolset/wix/blob/main/src/burn/engine/section.cpp) · [Squirrel Setup resources](https://github.com/Squirrel/Squirrel.Windows/blob/develop/src/Setup/Setup.rc) · [Electron-builder Windows targets](https://www.electron.build/docs/win/)
- **MSI.** Check the Windows Installer root CLSID in the compound file. Follow FAT and mini-FAT sectors to the Summary Information template and Property table. Read the needed prefix of the MSI string data to resolve `ProductName`, `ProductVersion`, and `Manufacturer`. The template describes Windows Installer's target platform. The installed executable architecture remains unknown. [Microsoft compound file format](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cfb/) · [MSI CLSIDs](https://devblogs.microsoft.com/setup/identifying-windows-installer-file-types/) · [Template Summary](https://learn.microsoft.com/en-us/windows/win32/msi/template-summary) · [Property table](https://learn.microsoft.com/en-us/windows/win32/msi/property-table) · [MSI string pool reference](https://github.com/mdsteele/rust-msi/blob/master/src/internal/stringpool.rs)
- **MSIX and Appx.** Read `AppxManifest.xml` or `AppxMetadata/AppxBundleManifest.xml` from ZIP. Get the single package architecture from `Identity.ProcessorArchitecture` or the bundle variants from application entries. Resource packages are skipped. Appx and MSIX share a package layout. Appxbundle and msixbundle share a bundle layout. Plain display names take precedence over internal identity names. [Package identity](https://learn.microsoft.com/en-us/uwp/schemas/appxpackage/uapmanifestschema/element-identity) · [App package formats](https://learn.microsoft.com/en-us/windows/msix/package/app-package-formats)
- **ZIP, 7z, CAB.** Inspect PE bytes from archive members. A complete pass with one executable can assign a main architecture. Setup names and opaque package entries leave it unknown. Libraries add architecture evidence for the archive. For compressed members, decode a PE prefix of at most 16 KiB. Preserve machine-only evidence when CLR or hybrid metadata falls beyond that prefix. Read stored CAB blocks on demand. CABs with only compressed or split payloads remain opaque. [7z format](https://www.7-zip.org/7z.html) · [Microsoft Cabinet](https://learn.microsoft.com/en-us/windows/win32/msi/cabinet)

JSON includes `platform` and, for Windows, the `windows` object. The existing `architectures` array stays dedicated to Mach-O. `windows.architectures` records observed binaries or declared package platforms according to `architecture_source`. `main_architecture` refers to a verified main executable, a single application package target, or a single variant in a bundle. Unverified or ambiguous cases leave it null. The booleans describe architecture evidence at that same scope. Runtime behavior, driver compatibility, signature validity, and dependencies require separate checks.

## Mac listing lookup and privacy

The site builds its listing set in [build-lists.js](https://github.com/ThatGuySam/doesitarm/blob/master/build-lists.js) and emits names, compatibility text, and listing paths via [makeSearchableList](https://github.com/ThatGuySam/doesitarm/blob/master/helpers/searchable-list.js). Its general search uses Stork text matching. For this lookup, the scanner needs a unique exact normalized name. A small set of publisher-checked aliases handles cases like Spotify Installer and Microsoft Visual Studio Code. When both sides have known publisher data, a conflicting publisher rules out the candidate. The UI says “Is this the same app?” and links to the listing with its published status.

The catalog is a static same-origin snapshot of the [search export](https://api.doesitarm.com/app-list-searchable.json), loaded on the first Windows lookup. Refresh with `node web/scripts/update-mac-catalog.mjs`. The browser matches the catalog in memory and keeps scanned product strings on the device. Windows metadata fields reject path-like strings and control characters. The existing Worker and client redaction still applies to output. Architecture inspection uses inert metadata reads. The transport follows validated redirects only from the submitted URL.

## Limits

The Worker uses the same validation, DNS/IP checks, redirect limits, byte and decode budgets, and deadlines as the macOS scan. Pasted direct Windows downloads use the existing range route. Page discovery still prefers macOS candidates. A pasted Windows download that redirects to a file can be verified by a range probe and sent through the same direct route. Session-gated and no-range origins require a local file.

The remote profiles bound archive candidate reads. Large solid 7z blocks, unsupported 7z filter chains, compressed cabinets, MSI cabinet payloads, and setup engines can hide binaries. Version resources or CLR/hybrid metadata far into compressed entries can be unavailable. MSI metadata inspection reads the first 32 directory sectors and bounded portions of property and string streams. DOS stubs or unsupported PE machine values can leave architecture unknown. Lookups depend on metadata quality and snapshot freshness.

## Fixtures

[windows_fixture.py](fixtures/windows_fixture.py) generates 33 inert PE, MSI, Appx, ZIP, 7z, and Cabinet fixtures. The checked-in files total 45,878 bytes. Run `python3 fixtures/windows_fixture.py` to regenerate them.

## Public URL evidence

The corpus uses official download endpoints and publisher or Microsoft architecture evidence. The input file [windows-downloads.json](corpus/windows-downloads.json) keeps the cases and source links. Each scan requests ranges only. It uses the native CLI, a 2 MiB transfer budget, and a 35-second deadline. The numeric columns show unique source bytes read and the full artifact representation size, including failures where the origin disclosed a size. A declared payload and a measured installer launcher can differ. Current-release aliases can change over time.

```sh
python3 scripts/windows-corpus.py target/debug/scan-cli corpus/windows-downloads.json \
  "$HOME/.cache/doesitarm-winscan/windows-observed.ndjson"
```
