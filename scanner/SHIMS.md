# Scanner shims

2026-11-24

A shim is a small offline input that preserves what the scanner reports about a particular artifact. Keep the original logical length and exact coverage during recording. Keep the status, error, container format and ordered architecture claims during reduction. An uncovered read is an error, including when the scanner would normally swallow a source error during optional inventory.

## Research and implications

- Zeller and Hildebrandt's delta debugging tests complements at progressively finer granularity against an interestingness predicate. C-Reduce uses a supplied interestingness test and format-aware transformations. Perses preserves syntax by construction. Hypothesis shrinks the intermediate choices that generate the input. For arbitrary recorded archives, try removing covered ranges, then replacing byte groups. If a codec or checksum makes those mutations unproductive, regenerate from archive-level inputs such as member names, ordering, methods and declared sizes. [ddmin](https://www.st.cs.uni-saarland.de/papers/tse2002/) · [C-Reduce](https://github.com/csmith-project/creduce) · [Perses paper](https://cs.uwaterloo.ca/~cnsun/public/publication/icse18/icse18.pdf) · [Hypothesis on compositional shrinking](https://hypothesis.works/articles/compositional-shrinking/)
- Linux hole punching deallocates blocks while preserving length, and userspace reads receive zeros. That works for authoring a virtual multi-GiB source. Replay needs an explicit coverage map so a zero-filled observed byte and a hole the parser never read have different meanings. A portable offset map supplies that distinction without filesystem-specific operations. [Linux fallocate(2)](https://man7.org/linux/man-pages/man2/fallocate.2.html)
- VCR records HTTP interactions for deterministic replay. HTTP byte offsets are tied to one representation, with `Content-Range`, status and conditional validators governing what a range response proves. Reuse the scanner's native range validation and retain status-only cassettes for pre-artifact failures. The byte reader can accept new splits and coalescing inside recorded coverage. [VCR](https://vcr.github.io/vcr/) · [RFC 9110 range requests](https://www.rfc-editor.org/rfc/rfc9110.html#name-range-requests)
- Restic identifies stored chunks by content and packs several together. Content hashes help deduplicate repeated evidence and verify integrity. At the 2 MB total target, a repository-wide chunk store and garbage collector would add maintenance with unmeasured savings. Start with per-capture deduplication and one gzip stream with a digest. [Restic repository format](https://restic.readthedocs.io/en/stable/100_references.html#repository-format)
- libarchive checks in small uuencoded archives next to focused ZIP and 7z reader assertions. zip-rs mixes tiny ZIP samples, minimized fuzz cases and source for generating near-4 GiB offset scenarios. Goblin pairs some object samples with C sources and Makefiles. Object writes tiny inputs directly in the Rust test before parsing them. The public 7-Zip tree and SDK provide codec reference code and format material. The fixture-tree inspection did not identify a comparable first-party fixture corpus, so libarchive's 7z reader tests provide the directly inspected archive examples. Generate structural cases where readable Rust or existing Python can express them. [libarchive ZIP test](https://github.com/libarchive/libarchive/blob/master/libarchive/test/test_read_format_zip.c) · [libarchive 7z test](https://github.com/libarchive/libarchive/blob/master/libarchive/test/test_read_format_7zip.c) · [zip-rs near-4 GiB test](https://github.com/zip-rs/zip2/blob/master/tests/append_near_4gb.rs) · [zip-rs fixture provenance](https://github.com/zip-rs/zip2/blob/master/tests/data/README.md) · [Goblin fixture sources](https://github.com/m4b/goblin/tree/master/tests/bins/elf/symver) · [Object round-trip tests](https://github.com/gimli-rs/object/blob/master/tests/round_trip/mod.rs) · [7-Zip source](https://github.com/ip7z/7zip) · [LZMA SDK](https://www.7-zip.org/sdk.html)

Raw captures can contain compressed vendor data and names that text filters cannot detect. Keep captures outside Git. Use generated archive contents with neutral fixture names for checked-in tests. Treat any unmodified vendor header excerpt as requiring a provenance and license review. Use the repository's existing license for authored fixture code.
